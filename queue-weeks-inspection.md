Historical inspection report — September 11, 2026, before the queue retention fix.

The defects and line numbers below describe the inspected historical version,
not the current implementation. See `queue-fix-verification.md` for the subsequent
fix. Links under `data/` reference excluded local evidence: they are unavailable
in a fresh checkout and are non-portable. No raw captures accompany this report.

Inspection result: the scraper does not always send all boards still available in the provider response. A live EPL capture proves a board is retained by parsing but removed during queue selection before serialization. The API preserved every board actually sent during this run. No scraper application, API, or display code was changed.

Live evidence was collected on 2026-09-11 in a bounded 90-second run, using the existing scraper with a separate diagnostic wrapper. The wrapper captured provider response bodies without headers, the exact string passed to fetch as the queue POST body, HTTP status and response body, and both requested display queue endpoints after each POST. It ran Firefox headlessly. Existing current-board/results posting behavior remained enabled. The first sandbox launch failed with EPERM; the approved external run succeeded.

All captured board records, including leagueId, provider leagueName, week, providerEventId, matchCount, startAt, endAt, isCurrent and queuePosition, are in [boards.md](data/queue-audit/boards.md). Provider classifications there are derived using the unchanged selector at capture time; POST positions are actual serialized array positions. Raw evidence is in data/queue-audit. The diagnostic runner and evidence artifacts are untracked local files; they have not been committed.

Trace and inspection findings:

1. Network interception: auto-sync.js:2859 handles GET /engine/shop/feed/events responses with HTTP 200, parses JSON and checks session epoch before and after reading it. At line 2901 it hands the response to the league monitor before reading visible fixtures. Independently, lines 6868–6902 issue authenticated requests for both league IDs every five seconds through separate scheduler lanes. Provider credentials are not part of diagnostic artifacts.
2. Parsing: auto-sync.js:798 reads every values(feed.events) board through parseFeedEventsBoards (line 847). Competition ID is f.b.a.a.d, falling back to f.b.a.d and then requested leagueId. An explicit request/payload mismatch throws; the outer parser silently drops any board whose parsing throws. Unknown league IDs are dropped by the monitor. Week is f.b.c.a, converted to a string; event ID is board.a. Matches come from f.b.c.c, mapped without visible-fixture filtering; blank identity rows are removed. All live parsed boards had ten fixtures.
3. FEED-EVENTS-ITEM: this is a compatibility-cache log, not a necessary pipeline stage for off-screen league posting. With the monitor enabled, these logs are emitted only when a board matches the visible first fixture, and occur after monitor processing. Their absence does not establish capture failure; the log also omits league and fixture count.
4. Per-league state: league-monitor.js creates isolated lanes for 21 and 78. Each accepted response replaces state.boards with a map keyed by (leagueId, providerEventId), rather than accumulating all previously observed boards. Current selection sorts by first fixture start time (fallback board start), chooses the earliest start at or after capture time, otherwise the latest dated board. Queue construction includes that board and boards with starts at least as late. It does not consult endAt, provider status, or the active tab. Stored earlier boards can therefore be excluded from the queue, as demonstrated for EPL.
5. Deduplication/staleness: a serialized lane rejects a capture older than state.capturedAt or an invalid session generation. The timestamp supplied by ingestLeagueFeed is Date.now() at ingestion, not request start time or provider version, so an older request completing later within the same session can still replace a newer snapshot. The queue hash is JSON.stringify(queue.boards); identical contents suppress reposting, failed HTTP posts retry on later feeds. The map deduplicates event IDs, but queue construction uses the original board array, so repeated IDs in one response are not independently removed there. Current-board post deduplication uses league plus event ID. These additional risks were found by inspection, not reproduced in this run.
6. Serialization: auto-sync.js:943 maps every selected board into boards[], including weekNumber exactly, leagueId, event ID, timing, expectedMatchCount and all matches. postFeedEventsQueue at line 6563 validates every canonical board (expected ten fixtures, valid match identities/teams/timestamps) before calling fetch with JSON.stringify(queuePayload). One invalid board blocks the entire POST. There is no visible-tab filter here. HTTP success is treated as success without separately checking a JSON success flag; all captured responses actually had success=true.
7. API contract: Virtual-Api/services/providerQueueImportService.js explicitly requires weekNumber and carries board.weekNumber through conversion. It also requires nonempty startAt, endAt and nextRefreshAt; null timing can fail validation even if scraper canonical validation passes. The controller returns 400 for invalid queues, updates the live queue, and schedules SQL persistence separately. HTTP acceptance and live queue readback do not prove SQL persistence.
8. API storage/readback: virtualEventStore.saveLatestQueue preserves its existing current event if present in the incoming list, then keeps only the suffix after it; otherwise it selects incoming position zero. This is another possible pruning boundary, but no extra API pruning occurred in the captured comparisons. Both /api/virtual/display/queue?provider=VirtualHorizon&leagueId=21 and leagueId=78 returned HTTP 200 after each POST. All four same-league readbacks matched the posted ordered event IDs, weeks, fixture counts and league IDs exactly.

Conclusion: captured EPL weeks can disappear between stored parsed boards and POST body because of the start-time classification/filter. Champions passed the complete observed feed through, including repeated week numbers. There is no evidence in this capture that the API dropped weekNumber or rejected any submitted board. The display was not changed or used to infer the result.
